================================================================================
EXPLANATION: WHY EVERY SECTION WAS 'General' IN EARLIER BASELINE REPORT
================================================================================
1. Root Cause in Legacy Ingestion (Phase 1):
   - In Phase 1 (app/ingestion/processor.py), documents were chunked and uploaded to the
     original 'enterprise_rag' Qdrant collection with payload schema:
       {"source": filename, "source_type": ..., "chunk_index": ..., "text": ...}
   - Crucially, the Phase 1 loaders did NOT parse or attach the 'section' metadata to the payload.
   - As a result, the 'section' key did NOT exist in any point payload in the legacy collection.

2. Fallback Mechanism in scripts/run_baseline_retrieval.py:
   - When evaluating baseline retrieval against the legacy collection, line 73 of
     scripts/run_baseline_retrieval.py executed:
       'section': p.payload.get('section', 'General')
   - Because 'section' was absent from every legacy payload, Python defaulted 100% of the
     retrieved points to the literal string 'General'.
   - Consequently, in baseline_retrieval.json, every single retrieved context was labeled 'General',
     even though the source documents (PDF, DOCX, HTML, PPTX) contained structured section headers.
   - This was resolved in Phase 2 by implementing structured section parsing across all document loaders.
